## Edge coverage carried by this plan

- SPK-03 empty (resolved, explicit): a missing or empty Message-ID normalises to null and falls through to the next key kind.
- SPK-03 encoding (resolved, explicit): equality is byte-wise after D-13 normalisation, and the local part is never case-folded.
- ING-02 encoding (resolved, explicit): RFC 2047 is decoded, NUL stripped, and lengths are counted in code points with no split surrogates.
- ING-02 empty (resolved, explicit): no text part gives body source `none` with empty text.

## Flagged assumptions

- A6 (RESEARCH): the `hdr:` hash inputs (Date, From, To, Cc, Subject, In-Reply-To plus size). The live spike (02-14) confirms or changes them before real mail is stored (02-19). If it changes them, the change bumps HDR_KEY_VERSION to `v2`, so any stored `hdr:v1:` key stays valid and is never reused for a different input set. Bridge synthesises a Message-ID when one is missing, so hdr: keys should be rare for Bridge mailboxes.
- `hdr:v1:` refines D-12's `hdr:<sha256 of stable headers>` with a version segment. The source prefix scheme D-12 locks (pm:, mid:, hdr:) and 02-03's check constraint are unchanged; the segment only makes a later input change additive.
