# Decisions (from ADRs)

Synthesized from 3 ADRs, all `locked: true` and Status: Accepted. No contradictions between them (see /Users/samuel/dev/sift/.planning/INGEST-CONFLICTS.md).

## ADR-0001: Multiple mailboxes, single owner
- source: /Users/samuel/dev/sift/docs/adr/0001-multiple-mailboxes-single-owner.md
- status: locked
- decision: (1) The mailbox is the unit of isolation; every table holding mail-derived data (messages, embeddings, labels, decisions, classifiers, rule sets, eval runs, flags) has a non-null `mailbox_id`. (2) Exactly one owner and no users table; web UI access is gated at the network level (Tailscale or LAN), not by in-app accounts. (3) Isolation is enforced by Postgres row-level security keyed on a per-request `app.mailbox_id` setting; anything that reads across mailboxes (the unified review queue) uses a separate role whose policy allows reading but is never used by training or retrieval. Application-level `WHERE mailbox_id = ?` filtering is still used, with RLS as the backstop. (4) Learning never crosses mailboxes: the classifier trains on, and the LLM retrieves from, a single mailbox's confirmed labels only. (5) Rules are per mailbox in `data/mailboxes/<slug>/rules.md`, with an optional `data/shared-rules.md` merged in for every mailbox; categories are defined per mailbox. (6) Isolation is tested: `evals/isolation/` seeds two mailboxes with look-alike emails and fails if either one's messages appear in the other's classifier training set, LLM prompts or explanations. (7) Credentials are per mailbox, supplied through environment variables (`password_env` in `config.yaml`), never stored in config files or the database in plaintext.
- scope: mailbox isolation, data boundaries, row-level security, Postgres, mail-derived data, classifier training, LLM retrieval, credentials, IMAP
- deferred (same source, "Alternatives considered"): multiple users / household support (deferred, door kept open); shared learning across mailboxes (deferred; if added must be explicit per-mailbox setting, off by default, covered by isolation tests). Rejected: single mailbox only; hosted multi-tenant service; app-level filtering as the only mechanism.

## ADR-0002: Tiered classification, trained only on the owner's labels
- source: /Users/samuel/dev/sift/docs/adr/0002-tiered-classification.md
- status: locked
- decision: Three tiers, cheapest first. Exact rules: rules in `rules.md` that can be decided deterministically in code (sender, domain, phrase). Classifier: each email embedded with a small local embedding model; a per-mailbox classifier (nearest neighbors plus logistic regression) predicts category and confidence, fast enough to retrain after every label. LLM (small, local): a 1B-class instruct model receives the owner's categories and judgment rules, the most similar confirmed examples, and the fenced-off email; output limited to the owner's categories by a JSON schema. A message moves to the next tier when no exact rule matches, the classifier isn't confident or isn't trained for that category yet, or it is selected for a spot check; if the LLM isn't confident the message goes to the owner's review queue. The classifier's training set contains only labels the owner confirmed or corrected; labels applied automatically by any tier, including the LLM, are excluded. Quick confirm: Sift periodically offers a small batch of recent LLM decisions for one-key approval; approved or corrected decisions become owner labels and join the training set; batches are filled first from categories below `min_examples_per_category`, then from the LLM's least confident decisions. Learning directly from the LLM ("distillation") is available only behind an experimental flag, evaluated with the eval harness (the classifier with vs without LLM labels on the synthetic inbox); enabling it by default requires a superseding ADR, and LLM labels must then be weighted below the owner's, dropped when the owner disagrees, excluded from the cold-start count, and excluded from spot-check comparisons.
- scope: email classification, tiered architecture, embedding classifier, LLM inference, training data governance, quick confirm, spot checks
- rejected (same source): LLM only; fine-tuning a small LLM; classifier only (no LLM); the classifier learns from the LLM by default.

## ADR-0003: Decision traces, and learning from relabels in the mail app
- source: /Users/samuel/dev/sift/docs/adr/0003-traces-and-mail-app-relabels.md
- status: locked
- decision: (1) Every classification produces a decision trace stored in the database (`decision` table), one span per tier that ran plus the final action and the rule set, classifier, prompt and model versions so the decision can be replayed; shown in the UI behind a "Why?" link; nothing is written into the mailbox. Exact-rules span: rules checked, matches, nearest miss. Classifier span: classifier version, top category scores, neighbor emails, threshold, escalation. LLM span: model, prompt version, rules included, examples retrieved, raw output, validation result, confidence. Action span: what was done in the mailbox and when, or that the email went to review. (2) Sift detects relabels made in the mail app and treats them as owner labels. Detection: per label folder (Proton Bridge exposes labels as folders like `Labels/Noise`), compare current messages to the last set seen on a polling interval (default 60 seconds); use CONDSTORE/QRESYNC where supported; store UIDVALIDITY and do a full folder resync when it changes. Identity: match messages across folders by `Message-ID` header, falling back to a hash of stable headers. State lives in each message's database row, not in time windows or memory. Echo suppression: record every change Sift makes and ignore it during sync. (3) Interpretation: Sift's label removed and another added = correction (owner label, the classifier trains); removed with nothing added = rejection without an answer (no training, asked in quick confirm); another label added with Sift's kept = ambiguous (no training, asked in quick confirm); message deleted = cleanup (ignored); Sift's own change = echo (ignored); no change however long = not a confirmation (never trains). (4) Corrections are routed using the trace: an exact rule caused it = suggest a rule edit, do not retrain; the classifier caused it = retrain the classifier with the corrected label; the LLM caused it = add the email as a retrieval example and to the mailbox's private eval set.
- scope: decision traces, relabel detection, IMAP polling, classification system tiers, exact rules, classifier, local LLM, training data, Proton Bridge, message matching
- open items (same source): Proton Bridge CONDSTORE/QRESYNC support and `Message-ID` consistency across label folders must be verified in an M1 spike, and the polling fallback must work without either; raw LLM prompts may need a retention limit (example: 90 days for full prompts, summary forever).
- rejected (same source): learning only from Sift UI corrections; treating labels unchanged for N days as confirmed; pairing removals/additions within a time window; writing the trace into the mailbox; flat log line per decision.
